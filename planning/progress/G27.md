# G27 — the re-label gate cannot fire on any ledger it writes

**Outcome: the defect reproduces, on 1.5.0, 1.7.0 and 1.8.0.** It is upstream in
`fledgeling-plugins`, nothing here was forked or patched, and what this repository now carries is
the report a person takes upstream plus a probe that re-asks the question of any future release.

## What was established

The brief's reading of the mechanism is correct and now measured rather than read. `reckon`'s
writer turns zero backing cases into `null` (`sorted(...) or None`), and `ratchet` reads `null` as
*this ledger predates the field* and continues — so the refusal below that branch is unreachable
for any ledger the tool writes. Both lines are byte-identical across 1.5.0, 1.7.0 and 1.8.0; the
field was introduced in 1.5.0 and has never worked.

Three things the brief left open, settled here:

1. **It is not confined to 1.7.0.** Every version carrying the field is affected, 1.8.0 included.
   1.0.0 through 1.4.0 have no such guard at all, and the probe reports them inconclusive rather
   than clean — the pre-field versions are the probe's own demonstration that its arming discriminates.
2. **The two conditions are already distinguishable in the serialised data, and the reader throws
   the distinction away.** A pre-1.5.0 ledger has no `backed_by` key; a 1.5.0-or-later ledger has
   it on every requirement row. Over the twelve ledgers in `planning/reckoning/`, four carry the
   key on no row, eight carry it on all. Across 310 requirement rows, 210 carry the key, 29 of
   those are `null`, and the value is an empty list on **none of them**. `crow.get("backed_by")` collapses key-absent and value-null into one answer. So the fix
   is better placed on the read side than the write side: reading key presence restores the guard
   over ledgers already written, where writing `[]` only helps ledgers written after the release.
3. **This repository owes no re-classing.** The brief's five rows — `REQ-021` to `REQ-025`,
   `verified-done` on nothing in the 1520 ledger — carry a passing citing case from the 1730 ledger
   onward, at `effect-witness`, `metamorphic` and `raster-visual` rungs with all three cited
   artifacts present on disk. The cause was `G26`: the five cases had left in a stash and were
   restored by it. The window closed because the cases came back, not because anything refused it.

## Evidence

`planning/upstream/reckon-relabel-probe.py`, run from this worktree. It builds both ledgers with
the tool under test from copies of this repository's own campaign and brief queue, picks its subject
from the registry rather than naming a requirement, clears that requirement's citations so it is
`observed` with zero backing, and puts the identical transition to `ratchet` three ways.

```
8 reckon installation(s) put to the probe: 3 affected, 0 not affected, 5 not measured
```

Per affected version, identically:

| arm | exit | outcome |
|---|---|---|
| as written, `backed_by` null | 0 | allowed — the defect |
| `backed_by` `[]` | 3 | refused, with the guard's own re-label message |
| `backed_by` key absent | 0 | allowed — the deliberate allowance, intact |

Watched to fail in the other direction too: against a patched copy in a scratch tree — carrying the
sentinel read plus the writer change, and never a plugin tree — the same probe reports **NOT
AFFECTED** at exit 0, the null arm refusing at exit 3 while the key-absent arm still passes. End to
end with both ledgers built by the patched tool, the real transition is refused. `selftest.py`
passes unchanged against the patch.

`selftest.py` also passes unchanged on every affected version, which is the second half of the
report: its guard arm and its pre-field arm are both hand-built rows, and an empty list has only
ever existed in that fixture. The arm owed upstream is one that builds through `build` and asserts
on what came out.

## What could not be done, and it is not G27's

**The worktree this item was dispatched into is unreachable from this session.** `.worktrees`
is a symlink onto an external volume, and partway through this session that volume began refusing
content reads to this process — `stat` answers, `open` returns EPERM, on every path under it,
including through the `/Users` spelling. The volume is mounted and healthy; `mount` and `df` both
report it normally. The first two reads of the session succeeded, so it changed mid-run.

**It is this process and not the machine**, which is the half worth recording: while this was being
diagnosed, another runner's `swift-test` was reading `.worktrees/M29` under the same volume, and a
third was running under `~/Dev/.g6-rebase`. So a fleet-wide conclusion drawn from one runner's EPERM
would have been wrong. What it costs is a runner that cannot reach its own worktree and has no way
to tell from inside whether the grant will come back.

The work was done on the same branch in a checkout on the internal disk, added with
`git worktree add --force <path> ai/g27`, so `ai/g27` is registered twice in `git worktree list` —
once at the unreachable path, once at the live one. The stale registration is removable with
`git worktree remove` once the volume is readable, and the branch is the same either way. No branch
change reaches the cause: it is a process-level grant, and granting it is the owner's.
