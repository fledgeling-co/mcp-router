## The pre-commit hook

Two faults, and only one of them is the one the brief named.

**The unset.** Git exports `GIT_DIR` for every commit inside a linked worktree — which is every
runner commit in this fleet — so anything the hook invokes carries that git dir into whatever
directory it walks into and runs against the runner's repository rather than the one it is standing
in. That is DEF-253's mechanism. Git does *not* export either variable for a plain commit in the
main checkout, so the line is inert on that path and load-bearing on the one the fleet uses. It is
preferred to an inventory because it holds for whatever the hook is asked to invoke next.

**The bypass the unset does not close**, found while proving the unset. Git runs a hook standing in
the *work tree*, and `GIT_WORK_TREE` moves the work tree without moving the commit. Committing from
the main checkout with it aimed at a linked worktree put the hook's cwd inside that worktree while
the commit still landed on `main` — the exact thing the hook refuses — and a cwd-derived
`git rev-parse --git-dir` read `.git/worktrees/<name>`, called it a runner and allowed it. The hook
now reads `git rev-parse --absolute-git-dir`, which answers from the environment git set up for the
commit and names the repository the commit is *going to*.

One case is an expected allow, recorded so nobody later "closes" it: with `GIT_DIR` aimed at a
worktree git redirects the whole commit there, so it lands on `runner` and `main` does not move.

`planning/hooks/prove-pre-commit.sh` runs six directions and eight assertions in throwaway
repositories, never touching this one, with two presence controls that exit 2 rather than print a
pass if they agree with the treated arm.

**How a fresh clone gets it.** The mechanism already existed and was half-built: `planning/hooks/`
is tracked, and its README documented a `cp` into `.git/hooks`. What was missing is any way to find
out afterwards whether it worked — an edited tracked hook and a stale installed copy look identical
from outside, which is a control believed armed with nothing checking. `planning/hooks/install.sh`
installs from the tracked source and `--check` reports drift by sha256, exit 1 on any mismatch,
absence, or lost executable bit. It derives the root and resolves `--git-common-dir`, so one run
covers the main checkout and every worktree.

**It is not installed on this machine, deliberately.** `--check` currently reports DRIFTED for both
hooks, which is correct: this branch changed the tracked source and nothing has been installed.
`.git/hooks` is shared by every linked worktree and three runners are in flight, so installing from
inside one changes the controls under all of them. That is the orchestrator's to run.

## The gate

`planning/runnable-path-gate.py`. **A file the repository can run must not name a path under
`/Users/` or `/Volumes/`.**

The family earns a gate, but only this line of it. "No absolute paths" would red on 62 non-runnable
files that are mostly legitimate, and a gate that can never go green gets softened until it means
nothing. This one is at zero and stays there.

It sits **beside** `planning/foreign-path-gate.py` (on `ai/g6`), not inside it. Two axes:

| | hand-written record | runnable file |
|---|---|---|
| **scratch root** (`/tmp`, `/var/folders`, `$TMPDIR`) | `foreign-path-gate` blocks | `foreign-path-gate`: RUNTIME, passes |
| **machine root** (`/Users`, `/Volumes`) | counted, never blocked | **this gate blocks** |

That gate's docstring declines the machine-path corner explicitly and gives the reason — *a scratch
path fails because the artifact evaporates, a machine path fails because the reader is on another
machine* — and argues that folding it in would add an uncoupled third axis to an item whose case is
that its own two halves are coupled. This is the remedy it names, for the executed half. It is also
separate for a duller reason: importing an unmerged branch's module would make this gate's arming
depend on `ai/g6` landing.

Counts, printed together and never blended: **N1** 134 runnable tracked files · **N2** 2 with a
machine path · **N3** 12 occurrences · **N4** 0 blocking. `~/` (55 lines), system locations (4) and
scratch roots (63) are counted and let through, each with the reason it is a different defect.

## Proof that each check can fail

| check | plant | result | restored |
|---|---|---|---|
| `runnable-path-gate.py`, real tree | G9's original defect verbatim — `cd /Users/lukerhodes/Dev/mcp-router/.worktrees/R2 \|\| exit 90` appended to `planning/run-gate.sh` | exit **1**, naming `planning/run-gate.sh:18` | sha256 `a286744e42fca177952fbec7b537ed0c38e345d21027cdbf87c131029bfa5815` before and after; exit 0 again |
| `runnable-path-gate.py`, presence control | 9 instances across BLOCK / WAIVED / CLEAN / NOT_RUNNABLE in a throwaway repo, including a bare marker with no reason that must **not** waive | all 9 read exactly; exits 2 if any is missed | throwaway, nothing planted here |
| `prove-pre-commit.sh` D4 control | the pre-G9 cwd-derived hook, reconstructed | ALLOWED the `GIT_WORK_TREE` bypass, as it must for D4 to be evidence | hook sha256 `cb8b60364e602760d3f4a41360efb382da17dee8b2424e4a4e814fce26d983c5` before and after |
| `prove-pre-commit.sh` D6 control | the same hook with the `unset` line stripped | the descendant resolved the *committer's* git dir; with the unset it resolved its own | as above |
| `install.sh --check` | nothing — run against the live state | exit **1**, DRIFTED on both hooks | n/a |

Both absence sweeps carry a presence control, because an absence check cannot detect its own
blindness: a sweep that has never been shown to fire returns zero for reasons it cannot tell apart.
Both controls run on every invocation rather than behind a flag.

Two instruments were themselves wrong first, and are recorded because the correction is the
evidence. `prove-pre-commit.sh` initially read its verdict from git's exit code, so
`ERROR:nothing-staged` was indistinguishable from a refusal and one direction reported REFUSED
having never reached the hook; it now reads the hook's own refusal text and names the other
outcomes. And the D4 presence control staged its probe into a tree the effective work tree did not
include, so it reported `ERROR:nothing-staged` and correctly refused to certify D4 — a control
declining to fire is the mechanism working, not a nuisance.
