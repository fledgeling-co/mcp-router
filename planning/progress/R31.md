# R31 — the caches a change outruns, and the one that goes stale while looking current

Three caches sit between a change and a call. Two of them are somebody else's store that the router
can only invalidate; the third is the router's own, and it is the one that can serve last week's
tool list while every check it has reports current.

## What shipped

`app/Sources/RouterCore/Caches/` — five files — plus `GET /caches`, `POST /caches/invalidate`, and a
content component on the manifest entry. Swift-only, declared as three `div-r31-*` rows.

| | |
|---|---|
| Manifest key | `UpstreamHash` **unchanged**; a second component recorded as `content` beside it |
| Consulted by | `mcp-router index` and the invalidation route. **Not `serve`** |
| Caches read | the manifest · `~/.npm/_npx` · `~/.claude/plugins/cache` |
| Caches written | `~/.npm/_npx` and `~/.claude/plugins/cache`, per entry, never wholesale without an acknowledged cost |
| Parity | 3 rows added, census `102 → 105`; `ToolUnion.isStale` byte-identical to the reference |

## The measurement the brief did not have

The brief said the manifest is keyed on command/args/env identity, so a change leaving that identity
intact leaves the manifest intact. Taken over the 21 upstreams configured on this machine on
2026-08-28, the exposure is not a corner case:

| shape | count | why the identity cannot see a change |
|---|---|---|
| `npx` with a floating spec | 3 | `media-gen-pro-mcp@latest`, `mcp-remote`, `@modelcontextprotocol/server-github` — same argv on every publish |
| `node <abs>/dist/index.js` | 4 | a rebuild in a local checkout rewrites the file the command names |
| an absolute binary | 8 | an upgrade replaces it in place |
| http / sse | 6 | no implementation on this machine at all |

**Fifteen of the fifteen stdio upstreams can change their code with command, args and env
byte-identical.** That is the whole item in one row.

The npx cache carries the same shape at rest: 48 entries, 2.0 GB, and `ref-tools-mcp` holds **two**
entries at 154 MB each — npm keys an entry on a hash of the spec string it was handed, which this
router cannot compute, so it digests all of a package's entries together rather than guessing which
one is live.

## Why the content component is beside the key rather than in it

`ToolUnion.isStale` is a byte-faithful port of `src/manifest.ts`'s `isStale`, and the parity harness
compares the two. Folding a content term into it would move a shared behaviour rather than add a
Swift-only one, and `RouterCoreTests/ContentIdentityTests` R8 asserts what that buys: a moved content
component leaves `isStale` false.

## The asymmetry that is the design: `index` asks, `serve` does not

A content probe wired into `serve`'s start-up sweep would re-derive every row the first time a router
met a manifest written before the member existed — and re-deriving a row means starting the child.
That is 21 subprocesses at boot, which is the exact cost the router exists to remove. It is paid on a
deliberate `index` and never on boot, and `ManifestIndexer`'s probe is optional and nil by default so
the differential oracle and every `cli` parity lane see the bytes they already compared.

## Three refusals, each a line of the brief

**Nothing is deleted that the router cannot cause to be re-fetched** is held by the types rather than
by care: `CacheRow.refetch` is `String?` and `CacheStep.refetch` is `String`, so a row naming no
refetch cannot become a step. Two of the 48 npx entries here hold no readable `package.json` and five
of the twelve plugin-cache directories are `temp_git_<millis>_<suffix>` clone leftovers with no
plugin layout; all seven survive even a request to clear everything.

**Narrow rather than wholesale.** A target names one server, one package, or one plugin version. The
acceptance lane asserts on the filesystem that a neighbouring package's tree is still there
afterwards, because a plan that reports a removal it did not perform and one that takes a neighbour
with it are both invisible to the stub probe the unit suite drives.

**An invalidation that cannot be scoped says so and asks.** `everyNpxEntry` answers 409 carrying the
byte figure the router just measured, and takes the request only when that figure comes back. A stale
acknowledgement is refused as firmly as an absent one, so the number a caller agrees to is always the
number that was just measured. And planning is the default everywhere: a body without `apply: true`
returns the steps, their bytes and the refetch command for each, and changes nothing.

## What this does not do, stated rather than implied

- **It does not poll.** Nothing re-checks content in the background; the two deliberate paths are
  `index` and the route. A package that moves between them is stale until one of them runs.
- **It does not re-index for you.** `POST /caches/invalidate` removes the trees and returns the
  server names in `reindex`; deriving the row needs a live pool, which the handler does not reach.
  `mcp-router index` and `POST /servers/:name/reindex` are what do it.
- **It cannot tell which of two npx entries for one package is live.** It removes both. That is
  correct for invalidation and would be wrong for a report.
- **A file stamp is size and mtime, not a hash.** A rebuild producing byte-identical output at the
  same mtime reads as unmoved. Hashing a whole built tree was the alternative and costs a walk of
  every entry point on every `index`.
- **It reads under `~/.npm` and `~/.claude`, which R28 deliberately did not.** That is this item's
  surface rather than a widening of R28's — the caches are not the router's to hold, only to
  invalidate — and every path goes through `CacheRoots`, which `MCP_ROUTER_CACHE_HOME` moves.
