F4 — Tracker states

Every state DESIGN.md §5 requires, and the exact ServerStateTracker.TrackerState value a surface reads to know it is in that state. F4 ships no surface. It ships the ability to tell these apart — which the tracker did not have, because pollLoop() discarded every typed error with try? and phase was pinned to .disconnected for any tracker built without a stream.

The derivation

Two independent facts, not one. load says what the last poll produced; stream says whether an event stream exists and what it is doing. They are separate because they fail separately: a healthy poll with a dropped stream is a real and common condition, and folding them into one value forces a surface to lie about one of them. The row that matters most is Partial — a snapshot that loaded and has since stopped refreshing is the ordinary failure in practice, and collapsing it to an error throws away data the user is reading.

Why .stale is its own case

.failed and .stale carry the same error and mean opposite things to a surface. .failed means there is nothing behind the error — no poll has ever succeeded, so the pane is the error. .stale means a poll did succeed, those servers are real, and only the refresh is broken — so the data stays and the error goes above it. A two-case model (ok / error) cannot express the second, and every surface built on it either throws away good data to show a failure, or hides a failure to keep the data. Both are wrong, and both are what the tracker forced before F4.

The two full-pane conditions

Both are .failed: no poll has ever succeeded, so there is nothing to show behind the message. The copy on both is ControlAPIError.headline, .advice and .actionLabel — shipped by F3, asserted verbatim against this file by ControlCopyTests. They are two different states, and F4's job is that a surface can still tell them apart after the poll loop has handled them: .routerNotRunning and .unauthorized are distinct values and neither degrades into "an error".

Loading, Default and Empty

The three load values a healthy tracker moves through. Empty is the one most often got wrong: it is a successful read that returned no servers, and it is only distinguishable from Loading because .loaded and .loading are different values — an empty array alone cannot tell you which you are looking at. The TypeScript router already shipped that exact bug once, reading a flat config as zero servers with no error at all.

Success — the recovery, in place

A poll succeeding after a failure is a state change, not an event to announce. The banner leaves, the rows update where they are, and nothing is toasted. This is the transition .stale(error) → .loaded, which a surface observes through updates() — the same subscription it already holds, with no separate success channel to subscribe to.

Disabled — and the state that did not exist

stream: .notConfigured is the second half of F4. A tracker built without an event stream is polling-only, which is a supported configuration — M1 runs one. The old type could not say so: phase defaulted to .disconnected and nothing ever moved it, so a polling-only tracker reported a dropped stream forever and a surface trusting it drew disconnected chrome over live data. No stream configured and the stream dropped are different conditions and now have different values.

The stream condition, in full

Four values, and the first is the one F4 adds. StreamPhase itself is F3's and is unchanged — R4 diffs F3's recorded fixtures against the Swift router, and widening a type it already pinned would move that contract. StreamCondition wraps it instead, so "there is no stream" is expressible without touching what a stream reports about itself.
