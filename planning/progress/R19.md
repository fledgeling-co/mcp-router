## What was built

**`src/lock.ts`** — the port of `ConfigMutationLock`. Same sidecar rule, same two timeouts and the
same `MCPR_CONFIG_LOCK_TIMEOUT_MS` override, same reentrancy guard, same unlocked fallback on a
filesystem with no advisory locking. Three places node cannot say what the Swift version says, each
declared in the file rather than left to be found:

- **No `flock` binding.** Node exposes none, so the lock is taken through macOS's `O_EXLOCK` open
  flag with `O_NONBLOCK`, which is `LOCK_EX | LOCK_NB` applied at open. Measured both directions on
  2026-08-22: node holding `O_EXLOCK` refuses a second process's `flock(LOCK_EX|LOCK_NB)` with
  `EWOULDBLOCK` and releases it on close; that process holding `LOCK_EX` refuses node's open with
  `EAGAIN`. One lock, not two — and `overlap-lock-shared` is the standing check that it stays so.
- **`fs.constants.O_EXLOCK` is `undefined`** on node v22.23.1/darwin, so the numeric value is used.
- **Thread-local becomes module-level.** The Swift guard is thread-local because `flock` is per open
  file description and two threads may legitimately block on each other. Node runs this on one
  thread and `body` is synchronous, so "held anywhere in this process" and "held on this call stack"
  are the same set.

One measurement changed a comment rather than the code: node already opens with close-on-exec set —
a child spawned while the parent held the lock did not keep it alive after the parent closed, with
and without the flag. `O_CLOEXEC` is passed anyway, and the comment says it is belt and braces.

**`buildManifest` gained a required `commit` hook.** The spawn stays outside; the bookkeeping and the
save happen inside, against a manifest loaded there. That is what makes node re-read per entry
immediately before saving, which is what Swift's `WatchIndexer.apply` already did — so `VER-R17-2`
closes by convergence rather than by a `surface.tsv` declaration, which is the outcome the triage
predicted. `commit` is required, not optional: a caller that could omit it would index a server and
mutate an object nobody writes.

**Swift's three sites** wrap load-merge-save in `ConfigMutationLock` on `manifest.json`'s own
sidecar. `WatchIndexing.swift`'s header said closing its window entirely was deferred child `D-w3`;
this is where that closed.

**`scripts/acceptance/parity-overlap.sh`** — the new lane, with two rows. It is a lane and not a row
in `parity-cli.sh` because that lane runs the two binaries sequentially over separate homes, so
nothing it can hold is ever live at the same time as anything else.

## Deviations, and things a reader should not discover for themselves

- **`ManifestIndexer` moved to its own file.** The comments recording why the load is inside the lock
  took `ServicePorts.swift` to 440 lines against a 400-line SwiftLint ceiling. The alternative was
  deleting them.
- **Three test suites stopped using `/router/manifest.json`.** The lock's sidecar is a real file even
  when the manifest lives in a `MemoryFileSystem`, and that path has no directory to put one in, so
  every write through them reported `could not open the lock file`. They now use a unique real
  scratch directory per test (`ManifestLockScratch`); the manifest bytes still go to memory.
- **`parity-gate.sh`'s coverage-by-group block walked a hardcoded list of nine group names.** A group
  outside it counted in the fraction and never printed. It was already swallowing `authserver`'s
  eight rows; `overlap` would have been the second. The list is now a preference and every group seen
  is printed. Nothing that computes coverage moved.
- **`mcp-router index` with nothing stale now writes nothing**, where it used to rewrite the file it
  had just read. That is what the Swift router already does, so it is convergence rather than a new
  behaviour, and no lane compares the file's mtime.
- **`POST /servers/:name/approve` answers 500 with the lock's own sentence** when it cannot take the
  lock, on both routers. Not 409: 409 asserts there was no pending change, and a run that never read
  the manifest does not know that. Reachable only under a contended manifest lock held past the
  daemon's 2000 ms bound.
- **node's `indexOne` reports a refused lock as the index's own error**, so `POST /servers` answers
  422 with it and adds nothing — the same answer it already gives for a server that would not start,
  and true: nothing was changed. Swift reports it as `cacheFailure` beside a refused write, which is
  R10's shipped shape and deliberately not moved here.
- **Under a refused manifest write the two routers still report differently** — the reference throws
  and exits 1 where this router prints `not cached` and exits 0. That is R10/DEF-049's recorded
  decision, it predates this item, and the overlap lane says in its header that it does not diff
  streams for that reason.
- **The cutover target and the census disagreed before this change and still do.** The gate reported
  `92 less 1 exclusion is 91 against a decided 82` before the lane existed and `94 less 1 is 93`
  after. The two rows this item adds move it by two; the decision is the owner's and this branch does
  not re-derive it.
- **`ManifestBookkeeping` line numbers cited in older comments were not re-checked.** Only the
  comments this change edited were re-cited.
