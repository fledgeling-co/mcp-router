## What was built

**A `Settings` scene, and the destination it replaces is gone.** `Destination.settings` had eleven
Swift readers and two shell ones; all thirteen are edited. `group` loses its optionality with the
ungrouped tail, because Settings was its only inhabitant. `ShellRestoration` is untouched and its
behaviour flips anyway: a stored `"settings"` now restores to Activity because `restoring`'s
`guard let` fails.

**Seven panes, and twenty-two of the mock's thirty rows are not built.** *(This read thirteen until
M15's gap-fix counted the mock's `.form-row` elements directly; see `M15-gapfix.md`.)* `SettingsPane`
carries the mock's `data-pane` order; `SettingsPaneCopy` carries every string. Router draws Endpoint,
Home, Idle reaper, Counting since, Copy, Kept resident, the warm chips and Show in Servers; Security
draws the token card, the forget action and the paired device; Menu bar draws the status-item toggle;
Advanced draws the two router file paths and the build line. Harnesses, Session analyst and Updates
draw their name, their line and one sentence saying where the thing is decided today.

**Everything M8 could set is still settable.** `Endpoint`, `Home`, `Idle reaper`, `Counting since`,
`Kept resident`, `Show in Servers`, the menu-bar toggle, `Token`, `Read from` and
`Forget the stored token` are all present, read back off the running window by
`m8-settings-menubar.sh`.

**A second fidelity surface.** `MeasureDump` renders `settings` in two states, and
`mock-fidelity-gate.sh settings` exits 1 with 97 findings, every one of them a divergence the
manifest declares.

## Deviations from the plan, each with its reason

**B1/B6's "copy the file and keep the original" does not compile.** `SettingsMetrics`,
`SettingsGroup`, `SettingsCard`, `SettingsRow` and `WarmChips` are all internal to one module, so a
second copy under `Settings/` is a redeclaration rather than an additive step. The atomic D0 removal
absorbs the move: `SettingsBoardParts.swift` and `SettingsBoardModel.swift` are `git mv`d and
`SettingsBoard.swift` is deleted in the same change that adds the window. Phases A and B are still
additive where they can be — the whole of `MCPRouterKit`'s half lands first and compiles alone.

**B4's seven pane files are five.** `HarnessesPane`, `AnalystPane` and `UpdatesPane` would be three
files identical but for which `SettingsPaneCopy` case they read, and the copy already lives in the
kit where a test reaches it. One `GovernedElsewherePane(pane:)` replaces them. Three views differing
in a constant are three places for the type role, the padding and the measurement id to drift.

**Four of the seven subtitles are authored rather than taken from the mock.** The mock's Harnesses
line promises four preferences that exist nowhere in either target, and its Session analyst line
describes a model that reads your sessions. `spec-M15` §2's fifth assumption forbids building a
control for a capability the product does not have; a *sentence* naming one is the same claim one
level up and is worse, because nothing about it looks unfinished. Router's line survives verbatim.
Each divergence is a cited row in the pairing file.

**`CommandGroup(replacing: .appSettings)` is removed rather than kept, and `MenuCommand.settings`
becomes system-provided.** C3 said to measure whether `⌘,` arrives implicitly before applying it a
second time. Measured: with both the scene and a `SettingsLink` declared, the running menu bar
carried **two** `Settings…` items, both reporting `AXMenuItemCmdChar` `,`. Declaring the scene is
what contributes the item. `SettingsCommandItem` is deleted with the block;
`ShellCommandRouter.openSettingsScene` and its injected opener stay, because they are how anything
that is not the app menu opens the window, and they are what makes the clause behaviourally
testable.

**§4's Paired devices row reads the inbox snapshot, not `PairingRecordStore`.** That type is the
*phone's* record of the Mac it paired with. What this Mac observes is
`InboxSnapshot.pairedDeviceName`, which the shell is already polling, and that is what the row
draws.

**`MeasureDump`'s state→scenario mapping became surface-aware.** The plan said no harness edit was
needed beyond a `Surface` case. It was: a state name identifies the mock's own frame, and the mock
draws different *conditions* under one frame name on different surfaces. The Servers board's
`v-empty` is a router that answered with nothing declared; the Settings window's is
`Settings are unavailable while the router is stopped`, which is the offline condition. The shared
mapping would have rendered a live window under the name of the stopped one.

**Three script edits the plan did not name.** `mock-fidelity-selftest.sh` needed `Settings/` in its
scratch tree — its control case went red the moment the real lint gained a directory that tree did
not carry, which is that guard working, but it would have left every spelling case below it
measuring nothing. `mac-shell.sh`'s A4 row-count check pinned `-ge 8`, which was the destination
count while Settings was one; it now derives the number from `Destination.swift`, the same oracle
the file already reads further down. And `axkit` gained window addressing — every verb resolved its
subject with `standardWindow`, which takes the first window the app reports, correct with one and a
lottery with two.

**`ActivityBoardRulesTests` was not enrolled in the settings file list**, against §9's list of four
suites. Its `boardFiles` is a local, Activity-scoped list whose own docstring says it is scoped to
the files that item owns; it is not one of the suites that reads `boardFiles + shellFiles`.
`settingsFiles` is folded into `ShellTestSupport.gatedFiles` and `animatedSurfaceFiles`, and
`ShellAppearanceTests`' and `ShellScaffoldRetirementTests`' `shellFiles` loops take it explicitly.

## The four D3 measurements

| Behaviour | Reading | Built |
|---|---|---|
| minimise and zoom dimmed | `AXCloseButton` enabled 1, `AXMinimizeButton` and `AXZoomButton` **present** and enabled 0 | nothing — the scene provides it |
| Escape closes | keycode 53 posted to the process left the window open | `.onExitCommand` ships; see below |
| the Window menu lists it | yes, under its own title, beside `Checks` and the debug `Design system` | `Settings` added to `mac-shell.sh`'s system-items list, per decision 20's fallback |
| the source list traverses on ↑/↓ | **not measured** — see below | nothing; `List(selection:)` with `.listStyle(.sidebar)` is unmodified |

**Escape is recorded as unmeasured rather than as absent.** `.onExitCommand` needs the window to
hold the keyboard, and this harness never activates the app, so a posted keycode-53 reaches no first
responder. The reading was negative both before and after the handler existed, which makes it
insensitive to the thing it would be testing. `UI_VERIFICATION.md` rule 1 forbids the activation
that would settle it. What *is* asserted instead is that close is live, by pressing the button
rather than reading its `AXEnabled`.

**Arrow-key traversal has the same shape and is open.** Moving focus into the list and reading
`AXSelectedRows` back needs the window to hold the keyboard for the same reason. The seven rows and
the single selection are asserted over the accessibility plane; which key moved the selection is
not.
