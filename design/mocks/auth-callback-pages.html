R5 — the authorization callback pages

The router's entire user-visible surface for OAuth is two HTML pages served once, on the loopback callback, into whatever browser the user authorized in. The Mac and iPhone authorization surfaces belong to M8 and I1; this sheet is the router half.

Each frame below renders the exact bytes the router emits. They are not restyled to DESIGN.md — see the divergence note.

State matrix — DESIGN.md §5 against this surface

StateHow it is met, with real copy
DefaultThe success page: “linear is connected” / “You can close this tab and return to mcp-router.”
EmptyStructurally impossible. The page has no collection to be empty of — it renders one outcome for one flow. Recorded rather than invented.
LoadingReal but unowned: finishAuth is awaited before any byte is written, so the browser shows its own progress indicator for the whole exchange. No skeleton is possible without changing the reference's response ordering.
PartialNot reachable — the exchange either yields tokens or throws. There is no half-authorized record: saveTokens writes tokens and authorizedAt in one write.
ErrorThree distinct pages, above: the provider's own error value; “the provider returned no code”; and the exchange exception's message. All three say what happened; none blames the user; none emotes.
SuccessIn place, no toast — the page is the state change. The app learns of it separately, by the flow's completed promise clearing pending and re-indexing.
OfflineThe router is not running ⇒ nothing binds 8880 ⇒ the browser's own connection-refused page. Ours cannot render; the recoverable surface is the Mac app's, and belongs to M8.
DisabledA stdio server cannot authorize: POST …/auth answers 400 “stdio servers do not authorize; their credentials are env vars” — the reason travels with the refusal, and no page is served.
OverflowLong names wrap rather than truncate (card above). Reference behaviour, kept deliberately for parity; noted as a defect, not as a design.

The divergence, stated rather than silently resolved

These pages do not use DESIGN.md's tokens, and R5 must not make them.

The reference paints #141220 ground, #eae8f5 primary and #a6a2c4 secondary. DESIGN.md specifies --ground #1E1E1E, --t1 #FFF, --t2 #FFF @55%. They disagree.

DESIGN.md is authoritative for UI decisions, but R4's differential parity gate diffs the Swift router's bytes against the TypeScript router's, and spec-R3 B65 names these as the recorded pages. Restyling them inside R5 would fail the one gate that proves the port is faithful. The restyle is therefore a deferred child scheduled after R4's cutover, and it must change both routers in the same commit. R5 emits the reference's bytes.

Two security findings in the reference, carried into this sheet rather than patched here.

Reflected HTML injection. PAGE(title, detail) interpolates without escaping, and detail on the provider-refused path is the raw error query parameter. Any page the user visits during a flow can reach http://127.0.0.1:8880/callback?error=… and have arbitrary markup rendered on that origin, and can settle the flow as failed.

No state validation. The callback reads code and error and never checks the CSRF state nonce, so a forged callback can drive finishAuth with an injected code. PKCE binds the verifier and blunts it; the missing check is still a gap. Notably the Swift SDK's OAuthAuthorizationCodeFlow.extractCode does enforce expectedState — so whoever builds the transport (R2) gets the check for free and would then diverge from the reference.

Both are cross-cutting: fixing either in Swift alone breaks parity, so both are reported to the orchestrator as items spanning R2/R4 rather than resolved unilaterally inside R5.
