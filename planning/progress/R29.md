# R29 — push a reload to live sessions

**Branch** `ai/r29` · **Spec** `planning/specs/spec-R29.md` · **Plan** `planning/plans/plan-R29.md`
**Evidence** `planning/evidence/R29-acceptance.md` · **Bundle** `planning/evidence/R29/`

## What changed about the item, before what changed in the code

The brief made one thing a precondition: *settle whether any programmatic way exists to make a
live session re-read, before building either path*. It is settled, and it inverts the brief's
own conclusion for the half that matters most.

`notifications/tools/list_changed` is in the client, over a standalone `GET /mcp` SSE stream the
session opens after `initialized` and holds for its life. Measured against a fixture server and a
`claude -p` session started for the purpose: **3 ms** from the push to an unprompted `tools/list`,
while the receiving session was inside a 25-second `sleep`. No model, no slash command, no person.
`planning/evidence/R29/exp-A-session-id-sent.log`.

The router was already serving that stream and keeping no reference to it — a fresh transport per
request and `res.on('close')` to discard it. **The entire gap was a registry**, not a protocol
limit, not a client limit, and not the `mcp-session-id` header (the same run with the header
suppressed behaves identically, `exp-B-session-id-suppressed.log`).

So the item ships two mechanisms rather than one, and the boundary between them is the
deliverable:

- **The tool list — the router tells.** Every attached session, busy or idle, ~100 ms, nobody
  needed. This is what meets the brief's first acceptance line.
- **Skills and plugins — the router asks.** Not in the MCP protocol, so the unix socket is the
  only lever, and what lands there is text. Ships **off**.

The brief's framing — *"the router asks and each session complies at its next turn"* — remains
exactly right about the socket, and is the wrong description of the tool list. Both are stated.

## Three things measured that would each have shipped a lie

1. **`send()` is silent over a closed stream.** The SDK returns without writing —
   `webStandardStreamableHttp.js:835`. A `delivered` count built on the resolved promise reports a
   push to nobody as a push to everybody. Bytes are counted instead, and the control arm requires
   `delivered=0` with nobody attached.
2. **`procStart` is UTC; `ps -o lstart=` is local.** Comparing spellings rather than instants
   classifies every live session on a non-UTC machine as `recycled` — reporting nobody reachable
   at the moment everybody is. The mutation arm returns the two assertions exactly inverted.
3. **One junk pid blinds `ps` for all of them.** Found by this item's own fixture:
   `ps: process id too large` prints nothing for the good pids and exits non-zero, and reading
   that as "nobody is alive" reclassified every live session as exited. One bad row in a registry
   the router does not own would have disabled the feature while reporting success.

## Not done, deliberately

- **The Swift router does not carry this.** Both mechanisms are in the TypeScript router; the
  launchd agents run the Swift one, so a stock install gets `404` on `/sessions`. The CLI says so
  rather than falling silent. Porting is R4's parity surface.
- **Nothing was pushed at a live session.** `mcpr sessions` and `--dry-run` were exercised
  read-only against the real registry — 13 reachable, 0 bytes sent. Behaviour against those
  thirteen is **unmeasured**, not proven, and `notifySessions` ships off so the default sends
  nothing either.
- **Making the router stateful** was not needed and not done: a GET stream carries no MCP session
  state, so the stateless design in `src/router.ts:409` is untouched.
