## The instrument that was off — DEF-029, closed

`make test-ios` was red at 52 failures across 35 tests when this run began, on an untouched `HEAD`
checkout as well as on the branch, and it is green at **36 tests, 2 skipped, 0 failures** now. The
cause was not this repo. The process-wide accessibility engine was off, so SwiftUI's
`_UIHostingView` vended an **empty element array** and every label assertion read empty and reported
`nothing was measured, so this proved nothing` — the honest verdict for a dead instrument, and
indistinguishable from inside the suite from a product that renders no copy.

The engine had been on by accident: something else on this machine had enabled it, which is why the
suite was green for months while depending on ambient host state no file in this repo controls.

The fix is in three parts, and the third is the one worth reading. Switching the engine on through
`_AXSSetAutomationEnabled` and reading `accessibilityElements` rather than
`accessibilityElementCount()` took the suite from 52 failures to 0 — and then `make all`, run
immediately afterwards on the same device, came back with **39**. The state is device-scoped and the
call lands on the *next* process: on a device left disabled, the run that re-enables it fails a
deterministic set of 15 test cases — identical set, measured three times — and the run after it,
unchanged, is clean. The 15 are exactly the ones hosting a `ScrollView`, and the tests that pass
alongside them are geometry, counts and negative assertions, so the green half of that run was
vacuous too. `test-ios` now runs a throwaway process before the graded one and discards its exit
code. Measured end to end: three runs with the call mutated to `(false)` drive the device into the
disabled state at 54 failures each, and the next run with the warm-up in place is 36 tests and 0
failures in 1.4 seconds.

Three arms, because everything else in that target rests on this one thing. Renaming the symbol
fails exactly the instrument check and nothing else, which proves only the resolution assertion.
Mutating the call to `(false)` on a device created for the arm reads **53 failures**, which is what
proves the other 35 tests depend on it. And the first run ever taken on a device whose engine had
never been live reads **0 failures**, which is why the warm-up is needed for an explicitly disabled
device and not for a fresh one. Both arm devices were deleted afterwards.

The instrument check is itself instrumented: it blocks on a probe hosting `ScrollView { Text }`,
read back through the same walk every other assertion uses, with a 20-second deadline. Two narrower
probes were built first and both were wrong in opposite directions — a bare `Text` reports the engine
live where 15 cases read empty, and a `ScrollView` read through the container path alone reports it
dead where 35 tests pass. A probe that answers differently from the thing it stands for answers a
different question.

Four hypotheses were refuted along the way — device contention, address recycling in the walker,
publication timing on a product surface, and machine saturation. The last was reported to the owner
as the cause before the probe ran, and it was wrong.
`X3-ios-unit-lane-empty-tree.md` carries the whole of it; the case is CASE-0126.

## What DEF-015 turned out to be

It was recorded as two clipped captures caused by a shutter firing during a board transition, with
the fix named as a settle in `capture-mac-glass.sh`. **That was wrong, and reading two numbers side
by side out of dumps the script already writes says so.** Every window in the run is 980pt and every
capture is 2096x1376; what differs is the split group inside — 988pt on Checks, 1044pt on Skills,
1119pt on Discover. `NavigationSplitView` lays out past the window and centres the excess, and the
origin moves left by exactly half the overflow in all three cases, which is what makes the clipping
symmetrical: the sidebar's section headers read `unning` and `brary` while the nav rows beside them
are whole, and `Manage marketplaces.` loses its ellipsis off the right.

So it is a product defect on **three** boards rather than a lane defect on two captures, and the
third — Checks, 8pt — was too small for anyone reading the picture to see. The app declares no
minimum window width anywhere, so nothing stops a user reaching this state; 980pt is an ordinary
size, not a stress case. `capture-mac-glass.sh` now prints `board width: examined=14 overflowing=3`
every run, reported rather than enforced, because three boards overflow today and a known red in
`make all` either blocks unrelated work or gets its assertion softened.

**Half of it then closed, and the mechanism was a chain rather than a board.** Each row's fixed
columns report a hard minimum width; the detail pane sums them; `NavigationSplitView` reports that
as its own minimum; and nothing ever reads it back, because this app opts into no minimum window
size and `windowResizability` defaults to `.automatic`. So the window proposes 980pt regardless and
SwiftUI *places* the oversized child centred — which is why the clipping was symmetrical, and why
the sidebar was paying for the detail pane's columns.

The fork went to the xAI lane (grok-4.6, xhigh) with the measured table and both candidate fixes.
It called them both second-best and named the propagation instead, and its answer on the third
question — SwiftUI placement plus `.automatic` resizability, not any documented split-view overflow
mode — is what the one-line fix then confirmed. `ContentZone` carries `.frame(minWidth: 0, maxWidth:
.infinity, alignment: .leading)` on `ai/x4`, and the same probe reads 0 of 8 overflowing where it
read 3 of 8. The sidebar renders whole again. The leading alignment is the deliberate half: it
decides who loses when the content still does not fit, and the answer is never the navigation.

**Then the other half closed, and it corrected the first half's diagnosis of what was too wide.**
The brief written from the split-group numbers said three boards' table columns had to flex. A
pane-level probe — every leaf's right edge against the window's — says the columns are not the
driver. Cutting Discover's `nameColumn` from 216pt to 96pt moved its content width by **zero**. It
is the controls row: a `.fixedSize()` segmented picker at 567pt beside a search field pinned at
240pt, in a 684pt pane. Skills is the same shape at 748pt. And Checks was never a content defect —
its real content ends at 1152pt inside a 1160pt pane, and the only thing past the edge is
`KeyClaimProbe`, the `#if DEBUG` test surface A21 needs, overhanging by 4pt. That 4pt was the whole
of its 8pt.

Each board gained a `searchMinWidth` of four units and declares its field
`minWidth:idealWidth:maxWidth:`. The picker cannot give a point back — that is what `.fixedSize()`
means, and it is right, because a segmented control has nowhere to put a truncated label — so the
field is the only control in the row that can. Every board now reads 980 of 980 with nothing past
the pane edge but a 1pt scrollbar.

**That probe was wrong on its first run, and the pixels caught it.** It read the frame's y where it
meant x — the last five fields of a dump row are x, y, w, h and a flag — and reported clipped
elements on seven of eight boards, Settings included, whose capture is whole from edge to edge.
Seven of eight is close to uniform, which `detector-defects.md` names as the signature of a dead
predicate rather than a broken product, and opening one screenshot settled it in under a minute.
The split-group gate was untouched by the bug because it only ever compared widths.

Both guards were armed, and one of them was a detector defect first. `capture-mac-glass.sh` now
fails on any overflow and refuses to pass on `examined=0`; all three arms were exercised. And
`ShellDetailWidthTests`' first version searched the raw source for the modifier it wanted — which
the doc comment three lines above the modifier also contains, so deleting the modifier left the
assertion green. **A predicate satisfied by the prose explaining it is not a predicate.** Comments
are stripped before matching now, and both halves were re-armed separately.

**Two guards on the capture script itself.** The run-level `FRONT_BEFORE != FRONT_AFTER` comparison

**DEF-035 — a stale incremental build reports failures that cannot be true.** Adding a 14th case to

Stashing the changed sources passed, unstashing failed, which reads as a real regression. It is not.
`Choice.live` is encoded in the spare inhabitants of `Scenario`'s tag; a new case shifts that
encoding, and stale `MCPRouterUI` object files compare a value that no longer means what they think.
`rm -rf app/.build` then rebuild: 1512 tests in 188 suites, green. The hazard for a campaign is the

returned the same hash — a dead predicate, not a stable one. The cause was the probe, not the

collected cases from lines below the declaration. That found a real gap (12 one-line enums in the

**DEF-038 — the rendered-quality gate has never been able to run, and nothing said why.** The

verdicts, the denominator and the arithmetic.

## Fourth sitting — test-campaign 0.9.1, and what its new gate found

0.9.1 adds a fifth failure mode to the four this campaign was already defended against:
*verifying a guarantee over a capability that never runs*. Its instrument is
`vacuity-check.py`, three passes plus a control.

**Two of the three passes are exact and both were run.** `unclassed` reads
`examined=20 findings=0` — every requirement whose text names an effect outside the
process already carries an `effect` field. `uncensused` reads `examined=5 findings=1`,
and the one finding is REQ-016, which already carries a `providerNote` saying the empty
census is deliberate: the pairing exchange is unimplemented (DEF-001), so the guarantee
"stores a record only after contact succeeds" cannot be violated by a build that never
contacts anything. The script reads `provider` and not `providerNote`, so it will report
this every run. That is the right shape for it to have — the note is prose and the field
is the census — and the finding is true.

**The third pass is not usable here, and its numbers are not published.** `blind` asks
whether any reader appears after the last mutating call in a test body, both matched by
name prefix, and on this codebase it measures the verb list rather than the suite.

With the shipped defaults: `examined=1820 mutating=3 blind=3`. All three are false.
`DEFAULT_READERS` is snake_case — `load_`, `get_`, `read_`, `list_` — and this is a
camelCase Swift codebase, so no Swift reader can match any of them; and the three
`mutating` hits matched the token `restart` inside their own function names. Both flagged
`WatchRestartTests` cases were read in full and both read extensively after the mutation.
Three findings out of 1820 with a predicate that cannot fire is not a low score, it is a
pass that did not run.

With a hand-derived camelCase list: `examined=1834 mutating=258 re-read-after=158
blind=100`. Of the 20 findings the script prints, six are `@Test` functions at all — the
other fourteen are test doubles and helpers, because the population is every `func` in any
file with `test` in its path. Two of the six real ones were read in full and **both
re-read**: `undoRestoresTheItem` calls `queue.all()` three times after `model.remove(...)`,
and `resetReindexesAnIndexFailure` reads `client.calls` after `board.reset(...)`. Neither
`all` nor `calls` was in the list I wrote.

So the pass reports 3 with one configuration and 100 with another, and every finding
sampled under either was false. `detector-defects.md` names uniform output as the signature
of a dead predicate and a flood as the signature of a broken one; this produced both, from
the same script, an hour apart. **DEF-048**, recorded as a detector defect. The campaign
claims no blind-mutation number.

**What the campaign gained.** Two cases at the `structural` rung, CASE-0149 and CASE-0150,
closing DEF-025 and DEF-028 — six assertions, six mutation arms, all six watched to fail.
The rung is `structural` rather than `outcome` deliberately: these read the view tree's
source to establish which view owns a control, and a source grep must not buy effect
credit. So the strict denominator rose from 74 to 76 while the numerator stayed at 58, and
the ratchet held rather than rising. That is the honest direction.

Two arms are worth naming because without them each fix would be closable by deleting the
thing it fixes. **A2** deletes the moved recovery action rather than moving it — without
it, DEF-025 is "closed" by removing the control entirely and the first assertion still
passes. **A5** adds centring to the shared block — without it, DEF-028 is "closed" by
centring all nine Settings states, which is one state's design applied to the eight the
design left-aligns.

One arm reported ARM INVALID before it reported RED: A5's first anchor matched zero times
because a trailing comment differed. Recorded rather than silently re-run — an arm whose
anchor misses is not an arm that passed, and the runner printing `ARM INVALID` rather than
`still green` is the only reason the difference was visible.

**DEF-031 closed** by owner decision, and the mock amended to the board that ships. The
comment written to explain the removal first NAMED the two removed buttons; the vocabulary
differential greps that file for control names, so prose explaining a removed control puts
it straight back into the in-design set. It points at the brief instead. This is the
inverse of the `ShellDetailWidthTests` trap already recorded here — there a predicate was
satisfied by the prose explaining it, here a predicate would have been tripped by it. Both
have the same remedy and it is worth stating once: **comments are part of the corpus a
text predicate reads.**

**DEF-047**, found while building R8's gate and larger than R8. `swift-sdk` 0.12.1's
`Error.swift:240` decodes JSON-RPC `-32603` as `.internalError(unwrapDetail(nil))` where
its four neighbours pass `unwrapDetail(message)`, so a server answering -32603 with a
message and no `data.detail` has its message discarded. Against a fixture the reference
records `MCP error -32603: Internal error: Authentication required` and the Swift router
records `[-32603] Internal error`. For the whole class of -32603 upstream errors the Swift
router tells the user strictly less than the reference does — and **no parity scenario had
ever exercised a JSON-RPC error carrying a detailed message**, which is why 82 proven rows
never saw it. That is a coverage gap in the parity suite as much as a defect in the SDK.
