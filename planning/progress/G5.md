
**The cache was denied rather than renamed, and that is a deliberate substitution.** The brief asked
for a rename; four other agents were running against that cache while this item was in flight, and
renaming a shared directory out from under them is a real failure I would have caused rather than
measured. A deny is also the stronger disproof: a rename leaves the bytes readable under a new name,
whereas any read of the path fails here. The two-way control:

```
inside the sandbox:  ls …/test-campaign/0.9.2/…/strict-check.py → Operation not permitted
outside it:          the same path lists fine
HOME inside:         /tmp/g5-nohome, 0 entries
```

## Open, and deliberately untouched

**X7 and X8 are not closed and were not edited.** Their scripts are in the tree now. That changes what a
runner here could do; it does not change what this item did. An edit landing only here forks the
instrument, and a script behaving one way in this repository and another way everywhere else stops
being evidence of anything. Both notes now say that rather than "nothing to edit".

**Which version is "the version the gates ran" is recorded three different ways, and I vendored the
one the repository names.** `ORCHESTRATOR.md`, `LEDGER.md`, the M28 docket and the X7 brief all say
0.9.2, and X7 points at 0.9.2's script directory as the thing to fix. The campaign's own artifacts
disagree: `defects.in.json` stamps three findings `found-by: test-campaign 0.9.1`, and
`RUN-2026-08-20.md`'s fourth sitting is headed 0.9.1. And the machine has moved again —
`installed_plugins.json` records **0.9.4** since 2026-08-21. The three gate scripts that matter are
byte-identical across 0.9.1 and 0.9.2 (`campaign.py`, `capture-lineage.py`, `witness-worklist.py`);
`strict-check.py` differs by 8 lines and `vacuity-check.py` by 80, the latter being 0.9.2's fix for
DEF-048, which the campaign itself reported. So 0.9.2 is 0.9.1 plus the correction the campaign
asked for, and it reproduces 0.9.4's numbers on this data.

**The wrappers are G5-C1, not this item.** Nothing in `Makefile`, `scripts/` or
`planning/test-campaign/bin/` resolves a skill directory, so there was no invocation to repoint. An
agent invoking the skill still loads the installed version.
