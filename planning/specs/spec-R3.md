> # R3 — Swift router: control API, auth, usage, registry
>
> **Depends on:** R1.
>
> Port `src/control.ts`, `src/auth.ts`, `src/usage.ts`, `src/registry.ts`. The wire format
> must match the TypeScript control API byte for byte — F3's client is built against it and
> the parity gate in R4 diffs both.
>
> Non-negotiable, carried from the TypeScript build:
> - **`command`, `args` and `env` are not writable through PATCH.** A control API that can
>   rewrite a command line is a control API that can run anything.
> - Caller identity resolves on the server's `connection` event (TCP accept), cached on
>   the socket. Resolving it at the end of a tool call loses every short-lived client.
> - Trending is a signed delta over a stated window, never a popularity level relabelled.

**Deferred child assigned to this item:** *make the router's caller attribution deterministic
rather than lsof-raced — F3's fixture capture raced the async lookup and recorded an
unattributable call, worked around with a capture-time guard.*

## What this item is really for

R1 established the pattern and this item inherits it: **a port that is merely plausible is
worthless to R4**, whose gate diffs two routers and must treat any difference it cannot explain
as a regression. Parity is the default; every departure is enumerated in *Declared divergences*
and every JavaScript accident kept on purpose is enumerated in *Preserved JavaScript semantics*.

What is different here, and what sets this item's bar, is that R3 has **a second oracle R1 did
not have**. F3 recorded 23 real control-API responses in
`app/Sources/MCPRouterKit/Control/Fixtures/`, captured from the running TypeScript router. Those
files are the contract twice over: F3's client decodes them, and R4 diffs against them. So this
item is checkable against bytes that already exist, before R4 is built — and a clause that cannot
be checked against them is weaker than one that can.

The fixtures also settle a question that would otherwise be a guess. **Object key order and
key *presence* are observable**, because `JSON.stringify` walks members in insertion order and
omits any whose value is `undefined`. `server-stdio.json` has no `cwd`, no `indexedAt`, no
`placard` and no `pendingChange` — not nulls, absent keys. And `usage` inside a populated row
serialises `calls, errors, projects, firstSeen, lastUsed`, which is not the declaration order of
the `ServerStat` interface but the order `UsageStore.record` assigns the fields in. A port that
models these as a Swift struct with `Codable` gets both wrong and passes every test that only
decodes.

### What this item owns, and where it stops

`control.ts` is written against a live `UpstreamPool`, and the pool is **R2's**, running
concurrently rather than merged. `router.ts` owns the socket and is also R2's. So the boundary is
drawn where the existing code already draws it:

| Concern | Owner | How R3 handles it |
|---|---|---|
| Request dispatch, every endpoint, every response byte | **R3** | A handler over a typed request → typed response. No socket. |
| The listening socket, request parsing | R2 | R3's handler is called by it. |
| The upstream pool (`status`, `pending`, `warmUp`, `clearPending`, `isLive`) | R2 | R3 declares the port protocol and ships a test double; R2 conforms. |
| Spawning a candidate to index it (`indexOne`) | R2 | Same: a declared port. R1 already split `buildManifest` on this line. |
| The OAuth callback listener on 8880 | **R3** | `auth.ts`'s own listener, not the router's. |
| The SDK-backed transport for a token exchange | R2 | `beginAuth` already takes it as a parameter; R3 keeps that seam. |

That split is not a convenience. It is what lets every clause below be verified now, with doubles,
rather than waiting on a sibling item — and it is the same seam the TypeScript already has, so it
costs no divergence.

## Acceptance criteria

The oracle for every later stage. Evidence must be a measurement, an exercised request, or a
red-green test — never "it looks right".

**Differential** means the expectation is generated by running the TypeScript implementation on the
same input, not typed by hand. **Fixture** means one of F3's 23 recorded responses, compared as
bytes.

### S — the semantic invariants

These bind **every** clause below. They exist because an out-of-family review of the first draft
defeated most of the original clause table with implementations that satisfied each clause as
written and were still wrong; the invariants close those classes rather than patching one clause at
a time. A clause is read as if each of these were appended to it.

| # | Invariant | Why it is here |
|---|---|---|
| S1 | **Truthiness is JavaScript's `ToBoolean`, wherever the reference uses it.** `entry.error ? …` means an `error: ""` is **false** and the cached tools survive; `!!u.warm`, `b.warm \|\| undefined`, `!b.name`, `if (!u)` and `error ? 422 : 200` are all the same test. A Swift `!= nil` is a different predicate and is wrong | An `error: ""` entry reporting zero tools passes every fixture and is a defect. R1 met the same hazard in `isStale` |
| S2 | **`??` is nullish, never truthiness.** `state`, `inFlight`, `callsServed`, `idleSec`, `projects`, `mcpServers`, `body ?? {}` and the two registry bases default **only** on null/undefined; `0`, `""` and `false` survive | R1's N3, in six new places |
| S3 | **`undefined` and `null` are different values.** `JSON.stringify` omits a member whose value is `undefined` and emits `"k":null` for one whose value is `null`. A Swift `Optional` collapses the two, so the wire representation must carry the distinction — `cwd: null` in a config serialises as `"cwd":null`, while an absent `cwd` is absent | The single most likely silent divergence in this item |
| S4 | **Object key order is ECMAScript `OrdinaryOwnPropertyKeys`**, not plain insertion order: array-index keys first in ascending numeric order, then the remaining keys in insertion order. `{"10":a,"2":b}` serialises `2` before `10` | R1 established this as N10 for skipped entries; it recurs here for `projects` maps and for preserved config members |
| S5 | **Strings are JavaScript strings.** Map lookups, object keys and sorts compare UTF-16 code-unit sequences with no normalisation, so `"é"` composed and decomposed are two distinct keys. Lengths that gate a comparison — `content-length`, the token length check — are **UTF-8 byte** counts | R1's `JSString` exists for exactly this; using Swift `String` as a key anywhere in this item reintroduces it |
| S6 | **The handler is a total function of its injected dependencies.** Every response is constructed from the config, manifest, pool, usage store and auth store on each request. Recognising a recorded state and returning recorded bytes satisfies every fixture clause and is explicitly a failure of this spec | The review defeated nine clauses with a fixture lookup table. The fixtures are *samples* of the contract, never the contract |
| S7 | **Order of operations is observable**, and every ordered sequence named below is part of the contract: a later step must not run when an earlier one fails, and no step may be reordered because the end state matches | Dependency failure and crash windows make otherwise-equivalent orderings distinguishable |
| S8 | **The unit of comparison is status + headers + body bytes + side effects + handled-disposition**, per branch. A branch that returns the right bytes while reporting "not handled", writing a file it should not, or emitting a log line it should not, fails | `handleControl` returning `false` after answering would let the caller answer twice |

## Amendments to the clause table

Two clauses state a general rule that is right, and each has exactly one enumerated case genuinely
outside it. Both are recorded here rather than by loosening the rule, because a rule weakened to
accommodate its own exception stops constraining the ordinary case — which is the case that matters.

### B12 — the one-member error body

`{"error": <string>}` is the shape of every **generic** error branch. Two branches carry more, and
both are the reference's own bytes rather than a liberty this port takes:

| Branch | Body | Clause |
|---|---|---|
| A candidate that failed to start, `POST /servers` | 422 `{error, hint}` | B28 |
| `POST /servers/:name/reindex` | `{name, tools, error}`, at 200 or 422 | B33 |

Everything else — 400, 401, 404, 405, 415, 409, 502 — is the one-member object exactly, and a test
that finds a second member on any of them is reporting a defect.

### B69 — "never a partial identity", scoped

**The conflict.** B69 as first written required *every* attribution failure path to yield an empty
identity, "never a partial one". B71 requires resolved values to **equal** what the reference
resolves for the same live connection. These cannot both hold, because the reference emits

```js
{ pid, client, cwd: cwd || undefined }
```

— so when `cwd` is falsy the reference **itself** emits a partial identity. Satisfying B69 as
written would have meant emitting nothing where the reference emits a pid and a client, which is
precisely the divergence B71 exists to forbid, and it would have shown up in R4's gate as a Swift
regression against a reference that was behaving correctly.

**The amendment.** B69 is scoped to its four enumerated *peer-identification* paths — no such pid,
a pid exiting mid-scan, a non-TCP socket, unlistable descriptors. Each of those must still yield a
wholly empty identity: none of them establishes *who* the peer is, so anything emitted would be
invention. The **`cwd` case is an explicit exception**: a resolved pid and client with an absent
`cwd` is a *complete* identity by the reference's own definition — the peer was identified, and one
optional attribute of it was not readable — and B71 governs what is emitted. This is the same shape
as B12's carve-out above and is adopted for the same reason.

## Preserved JavaScript semantics

Behaviour that is an artefact of JavaScript rather than a decision, kept because parity is what
R4 measures. Each is a way a careful Swift port silently diverges while looking correct, so each
gets a named vector (B59).

| # | Behaviour | The vector that catches it |
|---|---|---|
| N1 | `JSON.stringify` **omits** `undefined`-valued keys; it does not emit null | A `describe()` of a server with no `cwd`, no index and no placard — four absent keys |
| N2 | Object key order is **insertion** order, and `{...spread}` overrides keep the original position while new keys append | `usage` serialising `calls, errors, projects, firstSeen, lastUsed`, and a merged registry row keeping the official row's order |
| N3 | `Object.keys(…).sort()` orders by **UTF-16 code unit** | Env keys `"\u{1F600}"` and `"\u{E000}"`: the emoji sorts first in JS, last under Swift's `<` |
| N4 | `Number(x)` yields `NaN` for junk, and `slice(-NaN)` is `slice(0)` — everything, not nothing | `GET /usage?limit=abc` returning every record |
| N5 | `readTail` indexes a **UTF-16 string with a byte offset** taken from `statSync().size` | A log over 512 KiB containing multi-byte text: the reference cuts at a different character than a byte-correct implementation |
| N6 | `Math.min(Number(x ?? 30) \|\| 30, 60)` maps both `0` and `NaN` to 30, and lets a negative through | `/registry/search?limit=0` → 30; `?limit=-5` → `-5` |
| N7 | `Array.prototype.sort` is **stable** | Three registry rows with identical rank keeping arrival order |
| N8 | `localeCompare` on ISO timestamps, not `<` | Two `updatedAt` values differing only in a fractional-second digit count |
| N9 | `'k' in obj` tests **presence**, so an explicitly-undefined member is still "in" | A PATCH body carrying `warm: false` clearing the field, versus one omitting `warm` leaving it |
