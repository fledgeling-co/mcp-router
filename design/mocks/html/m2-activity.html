M2 — Activity design representation · every surface, every state

Activity — the live call log

Answers one question: what is my agent actually calling? Every row is one tool call the router observed — when, which server, which tool, which project, how long it took, and whether that call is what spawned the server. Nothing on this surface is computed, estimated or inferred; the router either logged it or it is not here.

DESIGN.md §6 No number is displayed that the router does not observe. The five columns map one-to-one onto UsageRecord fields in src/usage.ts — ts, server, tool, project/cwd, ms — plus cold, ok, err, pid and client which the row and the inspector show. There is no "calls per minute", no "time saved", no rate.

1 · Default — the populated board

§2 Rows are 24pt (MetricToken.tableRows, DESIGN.md's "Table rows — 24–28pt for dense lists"). The height never changes: it is the same value in the populated row, the skeleton row and the overflow row, so nothing jumps when data lands and a long name cannot push a row taller. §2 Instrument data is monospace — the age, the tool, the project and the duration. The server name is the one sans-serif label, because it is a name rather than a reading.

What each mark means, and what it deliberately is not

§2 exclusivity A successful call carries no indicator colour at all. The prototype paints every ok row's dot --live; that token means "a child process is running", and a finished call is not a running process. Reusing it would make the one green dot in the app mean two things. Only a failed call is marked, in --fail ("failed or tripped"), which is also the better information design — the eye goes to the four rows that went wrong rather than the two hundred that did not. Colour is never the only signal: a failed row also carries the error string in the inspector, and its accessibility label begins "failed".

§4 Cold start is a drawn glyph, never ❄. The prototype uses the unicode snowflake; §4 says icons are drawn, on one grid, at one stroke weight, using currentColor. It is a frost mark at the same 1.4 weight as every other icon, in --t2 — not --accent, which §2 reserves for selection, focus and the one primary action, and which on this surface would compete with the selected row.

§6 The subtitle is 28 calls since 09:12 · live. Both halves are observed: the count is the number of records the router returned, and since is UsageResponse.since — the moment the counter was last reset, which is what makes "no calls yet" meaningful rather than alarming. The third word is the stream's own phase.

2 · The row, the inspector, and overflow

§5 Overflow A tool name wider than its column truncates at the tail, the row stays exactly 24pt, and the full value is in the inspector — never a tooltip alone, never a wrap. The same rule covers the project column, where a deep path collapses to its last segment on the row and appears in full in the inspector.

§8 Keyboard. ↑/↓ move the selection and scroll it into view. Return is the view's one default action: it opens the inspector for the selected row. Esc clears the selection and closes the inspector — the shell's §8 rule is "dismisses the sheet, then clears selection", and this board has no sheet, so it clears. Space is §8's breaker toggle and this board has no breakers, so it does nothing here and is not claimed. Focus order is sidebar → table → inspector; the focus ring is the 2pt accent ring, drawn inset on a row so it is not clipped by the row above.

3 · The two filters

§3.6 Pop-up buttons — double chevron, showing a value — because each shows the current selection from an exclusive set. Not pull-downs, which have a static title, and not segmented controls, which switch views in place. Both are built from the records that are actually loaded: a session or a project appears in the menu only if the router logged a call from it, with its own call count beside it. A filter cannot offer a value that would return nothing.

A session is a pid and the client executable that owns it — the router resolves it once per connection through lsof, which is what turns "something called browser_navigate" into "the session working in ~/Dev/mcp-router called it". Where the router could not identify the caller, the record is grouped under Unattributed rather than dropped or invented; an unattributed record is still a real call.

6 · What this board deliberately does not have

Recorded so the omissions read as decisions rather than gaps.

  • No "reset history" control. The prototype's header has one. It is a destructive, un-undoable act on the router's ledger, so it needs a named-consequence dialog (§9) and a menu item (§3.9) — and a new menu command has to be added to M1's asserted command inventory. It is not in this item's brief, and it is filed as a child item rather than smuggled in here.
  • No search field. §8 binds ⌘F to "focus search"; this board has two filters and no text search, so ⌘F stays the shell's existing "this part of the app isn't built yet" and is not silently rebound.
  • No rate, no throughput, no "time saved". The router observes calls, durations and cold starts. It does not observe what would have happened otherwise, and §6 forbids showing a number it does not observe.
  • No sort controls. The log is chronological, newest first, because that is what the router's ring returns and what a live feed means. A sortable column would silently break the "new rows arrive at the top" contract.
  • No per-row actions. Nothing here is actionable — a call has already happened. The inspector reads; it does not offer.
