M7 — Evals and Cleanup

Two panes sharing one subject: evidence about whether a capability earns its place. Evals carries evidence of fitness; Cleanup carries evidence of use. Both are bound by the same rule, which has now bitten this product six times — no number and no sentence is displayed that the router does not observe.

0 · What the router observes, and what it does not

This section is the design. Everything after it is layout.

There is no eval runner, and for skills there never can be

Claim the prototype makesStatusWhat replaces it
8 graded cases on a skill Impossible. A skill is markdown the client loads into an agent's context. It never traverses the router, so the router can never observe it running, grade it, or time it. No future router item changes this. The five structural checks in §1 that the router genuinely performs when it reads a skill.
“3 of 8 passed”, a failing transcript, 18.4s Fabricated. No runner, no case store, no transcript, no timing. A per-check verdict beside the statement it judges, and nothing that reads as a suite result.
Skills filtered by runs === 0 in Cleanup Fabricated. M4 refused to model a runs field at all, for this reason. installed 4mo ago, never invoked is a claim about a thing the router cannot see. Reachability: a skill present in no client that could be read is loadable by nobody, which is observed. §11.
“Judging over 4 months of history” Hardcoded. The router reports its own window as UsageResponse.since, and that value moves every time the counters are reset. The observation track, §10 — the window rendered as an instrument, at whatever length it actually is.
“why it might be idle” → no reason found Speculation. The router does not observe whether a project was opened. Nothing. The column is removed; the evidence column states what was seen, not why.
Remove on a skill row Uncallable. The control API is read-only for skills. A dimmed control with its reason, plus Show in Finder, which is real. §13.
Memory or byte savings Already refused, by DESIGN.md §6 and by the prototype's own honesty paragraph. Nothing, and the pane says why in one sentence.

2 · Four verdicts, and why a pass is never green

VerdictMeansRenders
passThe router looked, and the condition holds. --t1 mono. Never --live.
failThe router looked, and the condition does not hold. --fail — its own meaning, “failed or tripped”.
unknownThe router could not determine it. Includes “never exercised”.--t3, with the reason adjacent.
not applicableThe check does not apply to this subject at all — OAuth on a stdio server.--t4, the disabled tier, dimmed in place.

A passing check is not drawn in --live, and this is a rule rather than a preference. DESIGN.md §2 binds --live to exactly one meaning — a child process is running — and states that nothing else in the app may be any of the three indicator hues. A check that passed is not a running process. The prototype paints its pass verdicts color:var(--live), which is the same defect DESIGN.md §10 already records against the prototype's phone Discover list, in a new place.

--fail is available for a failed check, because that is literally what it means. --attn stays reserved for the two conditions that genuinely want a human decision and that M4 already uses it for: a held version asking for more, and a marketplace whose origin moved. The consequence is that this pane has one loud colour and no decorative ones, which is what lets the breaker on Servers stay the only loud thing in the app.

3 · The fingerprint, and what invalidation looks like

The brief's one hard rule: an eval result is evidence attached to a version, so it must be invalidated when the version changes rather than carried forward. That needs a version to attach to, and both subjects have one the router already sends.

SubjectFingerprintWhy that field
serverhash The digest of the tool surface. It is the version of the thing being checked — more precisely so than a version string, which an upstream can leave unchanged while its tools move.
skillsource.plugin.pluginVersion A skill's version is its plugin's version, shared by every skill that plugin supplies. M4 established this and named the field accordingly.

Three renderings, and they are not interchangeable:

currentstored stamp equals the live one 0.4.1 · 2h ago The verdicts are shown as the current reading.
invalidatedstored stamp ≠ live stamp invalidated · was 0.4.1, now 0.5.0 Verdicts dim to --t4 and are labelled as judging a version that is no longer installed. They are never shown as a current pass.
unstampableno live fingerprint exists nothing to stamp Checks run and display, and no result is stored — there would be nothing able to invalidate it later.

Invalidation is not deletion. The invalidated run stays in the inspector's history under its own fingerprint (§1), because “this passed at 0.4.1 and has not been re-checked at 0.5.0” is exactly the fact the brief wants preserved. What is forbidden is carrying its verdict forward as though it judged the version now installed.

4 · A standalone skill cannot hold a result, structurally

M4 modelled SkillSource as a closed enum where the .standalone case has no version field at all — a skill dropped into a client's directory by hand genuinely has no version anywhere on disk. There is therefore nothing that could ever invalidate a stored result for it, and a result that can never be invalidated is a result that will eventually be a lie.

So the versioned check failing is not a nag about tidiness. It is the pane explaining its own behaviour: this subject's checks can be run and seen, and cannot be kept. The store refuses the write; it is not a rule the view remembers to follow.

failIt carries a version a result can be stamped against
This skill sits directly in a client's folder rather than coming from a plugin, so nothing on disk records a version. Its checks can be run and read, but not kept — there would be nothing to tell a stored result it had gone out of date.

8 · Run all checks — the sheet, because it costs something

Run checks on 6 servers and 14 skills?

Checking a server starts it, so that the router can read its tool surface. Six child processes will be started and left to the reaper as usual.

Nothing is changed and nothing is removed.

Not a destructive act, so not a destructive dialog — but it does spawn processes, and §3.4 gives … the meaning “opens a further view”. Cancel leads; the commit is the one accent-filled action.

10 · The observation track — the evidence, drawn as an instrument

DESIGN.md §10 records that the breaker is the only subject-mined element in the app and asks any new surface to add a second rather than another stock table. This is Cleanup's.

The whole question this pane exists to answer is how much do we actually know, and the answer is dominated by one number nobody thinks to look at: how long the router has been recording. “Never used” over 41 days is evidence. “Never used” over two hours is nothing at all, rendered identically by every table that shows only the verdict. So the track draws the observation window at its real length, against a 30-day reference, and a window too short to support the claim is visibly too short.

strong 0 calls · 41d observed Full track. 41 days of silence is a fact worth acting on.
0 calls · 9d observed Under a third. Readable as partial evidence.
weak 0 calls · 2h observed Almost nothing. Tinted --attn, because a decision taken on this evidence is one that wants a human to look first.

Every value on the track is observed: UsageResponse.since and the clock. The 30-day reference is a rendering scale rather than a claim, and the numeral beside it states the real figure, so nothing here depends on reading the bar. --attn is used at its own meaning — “wants a human decision” — and the weak case is exactly that.

And when the window is too short for the whole pane

▲
Call history was reset 2 hours ago. Everything below reads as never-used because there is almost nothing recorded yet, not because it is unused. Give it a few days before acting on this.

Fires when since is under seven days. This is the single most useful sentence in the pane and it exists only because the window is observed rather than hardcoded — the prototype's “judging over 4 months” could never produce it.

SubjectListed whenNever listed for

Or it indexed and declares tools == 0. “last used a while ago”. The prototype's last > 3600 is an invented threshold; a server used yesterday is used.
skill Every client that supports skills was read, and reports .absent. It is installed and loadable by nobody. Anything about invocation. The router cannot observe a skill running, so “never invoked” is not a sentence this pane is entitled to.

An unreadable client suspends the judgement rather than making it. If any skills-capable client is .unreadable, a skill that is absent everywhere else is not a candidate — it may be installed in exactly the folder nobody could open. Those skills are held out and counted in a banner:

12 · Removing a server — M3's named consequence, reused verbatim

Remove bigquery?

Its 18 tools leave every session's tool list.

2 values are set on this entry — MCP Router can see their names but not their contents, so it cannot put this back. Copy the entry first if you might want it.

Keep its call history

Every string above comes from ServersBoardModel.removeToolsConsequence and ServersBoardModel.removeConsequence, which M3 already shipped as public statics precisely so the wording is testable without a host. Cleanup calls them rather than writing a second set — DESIGN.md §6 asks for one name per state, and two dialogs describing the same act in different words is how that rule gets broken.

Why a dialog at all, when DESIGN.md §8 says removal is “undoable, never confirmed”. Because it is not undoable, and M3 measured why: describe() in src/control.ts sends envKeys: Object.keys(u.env).sort() — key names, never values. An app that cannot read a secret cannot restore an entry carrying one. §9's escalation clause is the governing rule here: friction scales to blast radius for genuinely destructive acts, as a named-consequence dialog whose destructive button is never the default. Cancel leads; Remove is not accent-filled. A server carrying no secrets gets the other branch of the copy, which says it can be re-declared exactly.

13 · A skill cannot be removed, and the pane says so

◆ legacy-deployold-marketplace · 0.9.0 loadable by no client
Remove — MCP Router only reads skills. Removing one means deleting files the client applications hold open, which it will not do behind their backs. Show it in Finder and delete it there, or remove the plugin from its marketplace.

The dimmed control stays in place with its reason attached (§5, §3.4) rather than vanishing, so the question “why can't I remove this one?” is answered where it is asked. This is M4's precedent: its board renders write controls dimmed with the same reason rather than offering an action it cannot make safe.

Show in Finder is a local action on a path the router already reported. It is not a second channel to the router and adds no new boundary.

Empty — nothing is reclaimable

Every declared server has been called at least once in the 41 days MCP Router has been recording, and every installed skill can be loaded by at least one client.

No action, because there is nothing to do and inventing one would be worse. The sentence names the window, so an empty list is readable as a real finding rather than a shrug.

Empty under a filter — not the same message

No skills are unreachable
Every installed skill can be loaded by at least one client. Two servers are still listed under All.

Loading, offline, stale, error

Identical in construction to Evals §5–§6 and composed from the same ControlAPIError strings, at Cleanup's own row geometry. A removal that the router refuses renders its error against that row with the router's hint, and the row stays in the list — a row that vanishes on a failed removal claims the removal worked.

Overflow

Names truncate at 180pt with the full value in the inspector. Row height is fixed at 44pt; the observation track's label is mono and bounded, so it cannot reflow the row.

Success

The row leaves the list in place, the segmented counts decrement and the sidebar badge decrements. Nothing is tallied. DESIGN.md §9: a never-used server was never deleted, so Cleanup does not report a total of what it removed — no “3 removed this month”, no running score.

18 · Deferred, with a named future source

DeferredWhyWhat would unblock it
A graded behavioural eval runner Needs a process that can call a server's tools with fixtures and grade the replies, plus somewhere to store cases. That is a router capability, and the Mac app may only speak to the router across the control API. A new router item — servers only. A skill never traverses the router, so no runner gives skills a graded result. Promising otherwise is the mistake M4's footer already made once.
Removing a skill from the app The control API is read-only for skills; the files are held open by the clients. A router-side skills write endpoint with its own preconditions and undo.
Restoring a removed server describe() never sends env or header values, so the app cannot reconstruct the entry. A router-side soft-delete with a restore endpoint. Until then the named-consequence dialog in §12 is the honest surface.
Renaming the destination from Evals to Checks Destination.title is a merged shared surface owned by M1; M7 does not edit shared surfaces. An orchestrator-scheduled item. Until then the pane's permanent subtitle carries the disclosure, which is why it is a subtitle rather than a footnote.
