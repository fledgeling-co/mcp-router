## The pre-commit hook

Two faults, and only one of them is the one the brief named.

**The unset.** Git exports `GIT_DIR` for every commit inside a linked worktree — which is every
runner commit in this fleet — so anything the hook invokes carries that git dir into whatever
directory it walks into and runs against the runner's repository rather than the one it is standing
in. That is DEF-253's mechanism. Git does *not* export either variable for a plain commit in the
main checkout, so the line is inert on that path and load-bearing on the one the fleet uses. It is
preferred to an inventory because it holds for whatever the hook is asked to invoke next.

**The bypass the unset does not close**, found while proving the unset. Git runs a hook standing in
the *work tree*, and `GIT_WORK_TREE` moves the work tree without moving the commit. Committing from
the main checkout with it aimed at a linked worktree put the hook's cwd inside that worktree while
the commit still landed on `main` — the exact thing the hook refuses — and a cwd-derived
`git rev-parse --git-dir` read `.git/worktrees/<name>`, called it a runner and allowed it. The hook
now reads `git rev-parse --absolute-git-dir`, which answers from the environment git set up for the
commit and names the repository the commit is *going to*.

One case is an expected allow, recorded so nobody later "closes" it: with `GIT_DIR` aimed at a
worktree git redirects the whole commit there, so it lands on `runner` and `main` does not move.

`planning/hooks/prove-pre-commit.sh` runs six directions and eight assertions in throwaway
repositories, never touching this one, with two presence controls that exit 2 rather than print a
pass if they agree with the treated arm.

**How a fresh clone gets it.** The mechanism already existed and was half-built: `planning/hooks/`
is tracked, and its README documented a `cp` into `.git/hooks`. What was missing is any way to find
out afterwards whether it worked — an edited tracked hook and a stale installed copy look identical
from outside, which is a control believed armed with nothing checking. `planning/hooks/install.sh`
installs from the tracked source and `--check` reports drift by sha256, exit 1 on any mismatch,
absence, or lost executable bit. It derives the root and resolves `--git-common-dir`, so one run
covers the main checkout and every worktree.

**It is not installed on this machine, deliberately.** `--check` currently reports DRIFTED for both
hooks, which is correct: this branch changed the tracked source and nothing has been installed.
`.git/hooks` is shared by every linked worktree and three runners are in flight, so installing from
inside one changes the controls under all of them. That is the orchestrator's to run.

### The gate on the install, and why it is not `--check`

Installing once does not close the class. `.git/hooks` is untracked derived state, so it can drift
again with nothing going red — and `--check`, written to detect exactly that, was **invoked by
nothing**: no Makefile target, no goals script, no hook. That is this item's own subject one layer
up, and it is the mechanism by which the hook reached a third hand-off: two verifiers recorded the
gap, and no instrument could.

`--check` cannot be the lint member as it stands. CI runs `make lint` on a fresh
`actions/checkout@v4` clone, where `.git/hooks` holds only the samples, and `--check` reds on
ABSENT — so wiring it in turns CI permanently red for a reason unrelated to the tree.

`--gate` splits the two states `--check` conflates, because only one of them is a lie:

* **DRIFTED** — an installed copy that silently disagrees with the tracked source. It claims to be
  a control and is not. Red always, whatever the worktree count.
* **ABSENT** — nothing was ever installed, so nothing claims to be armed. Red only where linked
  worktrees exist, which is exactly where the hook has a job: it exists to tell the main checkout
  apart from a runner's worktree, and with none there is neither.
* **NOT EXECUTABLE** — an installed hook that cannot run. Red in every mode.

The discriminator is counted from `git worktree list`, not sniffed from the environment. A real
fresh clone reports 1 worktree and no hooks; this checkout reports 29. Wired into `make lint` as a
recipe step rather than a target, for the reason `grok-4.6` gave in the round above:
`planning/goals/lint-except-citation-ratchet.sh` parses the `lint:` recipe, so a separate target
would be invisible to it.

### A fleet-wide hazard this round hit, and it is not G9's subject

**`git stash` is repository-global, and this fleet runs 28 linked worktrees off one `.git`.**
`refs/stash` is a single shared stack — it is not per-worktree the way `HEAD` and the index are. A
runner that pushes a stash and pops it a moment later is not guaranteed to get its own work back:
any other runner stashing in that window lands on top, and each pops the other's.

It happened here, twice, and both times it was caught by an unrelated instrument rather than by
noticing. `git stash -q -u` was used to read a gate's figures at HEAD and then restore — a
reasonable-looking way to get a clean baseline. What came back was another runner's uncommitted
work: a `SETTLED`-disposition change to `planning/sweep-control-gate.py`, and a
`planning/sweep-controls.json` carrying 20 dispositions for exactly the inherited backlog, which is
another item's job and not this one's. This branch's own Makefile and `install.sh` edits went the
other way and were not recoverable from the stash stack or from unreachable commits; they were
rewritten from the session's own record.

Both foreign changes were **preserved before being reverted** rather than discarded, because the
race may well have left this worktree holding the only copy:

| file | saved to |
|---|---|
| `planning/sweep-control-gate.py` | `/tmp/g9-foreign-recovered/sweep-control-gate-SETTLED-disposition.patch` and `.py.full` |
| `planning/sweep-controls.json` | `/tmp/g9-foreign-recovered/sweep-controls-20-dispositions.patch` and `.json.full` |

Their owners should take them back from there. **Neither is in this branch**, and both gates were
re-measured after reverting: `sweep-control-gate.py` reads 20 UNDISPOSED / 21 FINDINGS, identical
to `main`.

The rule that follows is short: **in a shared-checkout fleet, do not use `git stash` to get a clean
tree.** To read a gate at HEAD, run it against a throwaway clone or a `git worktree add` of the
commit, or read the file with `git show HEAD:<path>`. Nothing about this is G9's finding — it is a
hazard of the fleet's own shape, filed here because this is where it was measured, and it is a
sharper version of the same family: an operation that looks local and is not.
